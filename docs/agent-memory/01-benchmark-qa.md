## 2026-11-17

### Q1. "ccr-8bdebdb5-0eh9qw 이 브랜치 내용 파악 가능해?"

가능했습니다. 사용자의 다른 저장소에 있는 브랜치로, 전날 클라우드 세션이 한 1차 검증이었습니다.

- 내용: Agent Substrate를 kind에 설치하고 gVisor checkpoint/restore를 재려던 작업.
- 결론은 "조건부 가능"이었고, 그 환경이 cgroup v1이라 worker pod가 뜨지 못해 부하 실행까지는 못 갔습니다.
- 이 저장소의 작업은 그 1차 검증을 이어받아 Mac에서 끝까지 돌린 것입니다.

### Q2. "지금 memmachine고 dynamo 관련 리소스 잡아 먹고 있는 것들 전부 해제하고, Agent substrait 관련 동작 가능성 파악 진행해봐."

Mac의 다른 작업 컨테이너를 중지하고(삭제는 하지 않음) 검증을 시작했습니다.

- OrbStack VM은 cgroup v2라 1차 검증이 막혔던 원인이 없었습니다.
- `/dev/kvm`이 없어 microVM 방식은 이 Mac에서 확인할 수 없습니다. gVisor 방식만 봅니다.
- Go는 시스템에 설치하지 않고 작업 폴더의 `toolchain/` 안에 받았습니다.

### Q3. "내가 하고 싶은 궁극적인 목표는 다수의 agent들이 활성/액티브를 반복하고 다수의 에이젼트들이 체크포인트를 생성하는 환경을 모사해서 실제 문제가 발생하는지를 확인하고 싶은거야. 실제 확인은 회사 서버에서 할거지만, 이게 가능한지를 먼저 판단해보려고해. 에이전트를 실제로 돌리는 것도 당연히 한계가 있지 자원이슈로. 가상의로 확인해 보려는거야."

그 목표에 Agent Substrate의 부하 도구가 맞습니다.

- **가상 Agent:** 실제 LLM을 돌리지 않습니다. 더미 프로그램(glutton)이 대본(YAML)대로 CPU·메모리·디스크를 쓰고 쉽니다.
- **활성/비활성 반복:** 대본의 단계 사이에 쉬는 동안 재워지고, 다음 단계에서 깨어납니다. 세션 수만큼 동시에 돕니다.
- **checkpoint는 진짜입니다.** gVisor가 실제 메모리를 디스크에 쓰고 객체 저장소로 올리므로 스토리지 부담은 실제 값입니다.
- **Mac에서 알 수 없는 것:** 규모와 절대 수치(VM 메모리 8 GB라 동시 몇 개 수준), microVM 방식, x86과의 차이.

### Q4. "응 이 내용을 위해 내 github에 새로은 repo 하나 따서 거기서 작업해 내가 당겨서 회사에서 그대로 재현할 수 있도록"

이 저장소(`agent-suspend-bench`)를 만들었습니다. 당시에는 비공개였습니다(Q23에서 공개로 바꿈).

- actor 1개를 3번 재웠다 깨우는 동안 상태(카운터 1→4)가 이어지는 것을 확인했습니다.
- 재우기 0.21~0.32초, 깨우는 첫 요청 0.11~0.27초. 메모리가 몇 MB뿐인 데모라 하한선입니다.
- snapshot은 노드 로컬 `/var/lib/ate/snapshots/` 아래에 약 4.5 MB, 객체 저장소에 zstd 압축본 약 2.4 MB가 남았습니다.
- macOS 기본 bash 3.2에서 배포 스크립트가 죽어 bash 5를 작업 폴더 안에 두었습니다. Linux에서는 해당 없습니다.

### Q5. "agent-infra-benchmarking 이게 google cloud 전용이라던데 우리가 사용 하지 못하는지도 한번 봐줘."

그대로는 회사 서버에서 쓸 수 없고, 우리 목적에는 필요하지도 않다고 판단했습니다. 코드와 문서를 읽은 판단이고 실행해 보지는 않았습니다.

- 실행마다 Terraform으로 GKE 클러스터를 만들고, snapshot 위치를 GCS로 고정하며, GCP 서비스 계정이 없으면 설치를 거부합니다.
- "bare metal" 옵션은 GKE의 metal 머신 타입을 뜻합니다. 자체 서버가 아닙니다.
- 저장소 루트에 LICENSE 파일이 없습니다(파일 헤더는 Apache 2.0).
- 떼어 쓸 수 있는 것: Go 부하 생성기, 실제 OpenClaw Agent를 가짜 LLM에 붙이는 워크로드. 다만 직접 배선해야 합니다.
- 자세한 비교는 `docs/workload-patterns.md`.

### Q6. "완료되면 회사에서 뭘 어떻게 받아서 어떤 단계로 진행해야 무엇을 확인할 수 있는지 알려줘."

### Q12. "11page에 메모리 한도가 SSD 용량이지?"

아닙니다. RAM 쪽 한도입니다.

- Agent Substrate는 snapshot을 객체 저장소로 올릴 때 압축(zstd)과 전송에 쓸 작업 공간을 RAM에 잡습니다. 이 합계를 노드당 512 MiB로 묶는 설정이 `--upload-memory-budget`입니다.
- 한도를 2 GiB로 올려도 디스크에 쓰는 양은 같았습니다(재우기 1회당 약 310~320 MiB).
- 달라진 것은 대기 시간입니다. 압축·업로드 구간이 7.2초에서 0.84초가 됐습니다.
- 대가는 RAM과 CPU입니다. 가용 메모리 최소값이 2.6 GiB에서 1.8 GiB로, CPU 평균이 39%에서 52%로 바뀌었습니다.

### Q13. "아 압축을 하고 처리를 위해 메모리 공간이 필요한데 공간이 작아서 락된단거지?"

거의 맞습니다. 두 가지만 정확히 합니다.

- RAM이 실제로 모자란 것은 아닙니다. 가용 메모리는 2.6 GiB 이상 남아 있었고, 막은 것은 설정값입니다.
- 락이 아니라 대기열입니다. 업로드를 시작할 때 예산에서 메모리를 예약하고, 남은 예산이 없으면 앞선 업로드가 끝날 때까지 기다립니다(소스에서는 가중치 세마포어).
- sync 방식은 업로드가 끝나야 재우기가 끝난 것으로 치므로 이 대기가 재우기 시간에 그대로 들어갑니다.
- 한계: 예약하고 기다리는 구조는 소스에서 봤고 효과는 실험으로 확인했습니다. 대기 시간 자체를 따로 재지는 않았고, 이 설정이 압축 병렬도도 함께 바꾸므로 두 효과를 나눠 보지 못했습니다.

### Q15. "추가된 원인 분석 잘 해석이 안된다. 2분뒤 또다른 문제에 대해서도 잘 이해가 안가고" / "이 내용이 장표에 잘 표현이 안되는 것 같아서."

"업로드 창구" 비유로 다시 설명하고, 원인 분석을 세 장으로 다시 그렸습니다.

- **기본 한도에서 느린 이유:** 큰 파일 하나가 480 MiB를 예약해 한도(512 MiB)를 거의 다 씁니다. 사실상 창구가 하나입니다. 창구는 초당 0.78개를 처리하는데 요청은 초당 1개씩 와서 줄이 생깁니다.
- **한도를 올리면 빨라지는 이유:** 작업이 빨라지는 것이 아니라 기다림이 없어집니다. 9.5초(작업 0.8초 + 대기 8.7초)가 0.5초가 됩니다.
- **2분 뒤에 다시 느려진 이유:** 창구가 늘자 업로드 여러 개가 같은 CPU와 RAM을 나눠 쓰게 되어 하나하나가 느려졌고, 2 GiB도 다시 찼습니다. 증상은 같지만 원인은 CPU와 메모리입니다.
- 어느 쪽에서도 디스크가 한계였다는 증거는 없었습니다.
- 한계: 2 GiB 실행 두 번 중 한 번의 기록입니다. 다른 한 번은 끝까지 빨랐습니다.

### Q18. "오케이 이제 스몰 모델로 동작하는 회사 에이젼트 환경에서 진행사항을 문제 없이 처리 할 수 있도록 핸드오프 만들어줘. 필요한 정보 요청하면 내가 기입해 줄게. 가능하면 상황에 맞게 처리 가능한 수준으로 만들어 주면 더 좋고."

### Q27. (2026-11-19) "새로운 이슈로 결과 분석 요청 보냈어. 확인해봐" (issue 2번, Linux 서버의 S·T·A·B·C 단계 결과)

결론: 재우기(suspend)가 느린 것은 저장 장치나 메모리 부족 때문이라기보다, 객체 저장소로 올리는 단계가 한 번에 몇 개만 처리하는 "창구"여서 줄을 서기 때문일 가능성이 가장 높습니다. 아직 추정이고, 이미 만들어 둔 E·F 단계로 가릴 수 있습니다.

- 근거 1: 모든 실행(B 8/16/32 세션, C 24/48/96 세션)에서 완료 속도가 초당 1.1~1.3개로 같고, 재우기 시간은 세션 수에 비례해 늘었습니다(4.4초 → 54초). 처리 속도가 고정된 창구 앞에 줄이 길어질 때의 모양입니다.
- 근거 2: 재우기 시간의 대부분인 `persist` 단계는 sync 방식에서 "객체 저장소에 올리기"를 포함합니다(`src/substrate/cmd/atelet/main.go`의 `UPLOAD_MODE_IMMEDIATE` 분기). 올리기는 512 MiB 공유 한도(`--upload-memory-budget`, `pkg/objectstorage/upload.go`)에서 자리를 받아야 시작합니다.
- 근거 3: 메모리 dump(`worker_checkpoint`)는 0.3초이고 그 뒤에 worker가 비워지므로, 재우기가 줄을 서 있어도 깨우기는 빠를 수 있습니다. 깨우기 0.30초는 "실행된 깨우기 호출"의 시간이고 교체 한 건의 전체 시간이 아닙니다.
- `target_rps=8`은 1초 tick마다 최대 8쌍을 한꺼번에 내보내는 요청 속도입니다(`turnover.go`의 `tick`). 고르게 나눠 보내지 않고, 쌓아 둘 수 있는 양은 `rate+1`로 제한됩니다.
- 메모리 한도 도달(`memory.peak` = 32 GiB)은 snapshot 파일의 page cache만으로도 생길 수 있습니다. `memory.stat`의 anon/file 구분이 없어 원인을 가릴 수 없습니다.
- 다음 실험: `scripts/stage.sh`의 E 단계(async)와 F 단계(업로드 한도 2Gi 대 기본값)가 바로 이 구분을 위한 것입니다. 실행별 cgroup 메모리 기록, turnover 상태 수, 장치별 I/O 대기 시간 수집을 더해야 합니다.
- issue 본문에서 찾은 점: C_turn48의 `persist` p50(34.73초)이 suspend p50(28초)보다 큽니다. 두 값의 집계 대상이 다른 것으로 보이며 확인이 필요합니다.

### Q28. (2026-11-19) "8/s로 교체를 한다고 하면 1초당 8개를 재우고 8개를 깨우는 요청을 할 거잖아. 1초에 시작한 재우기가 완료가 안 된 시점에 다시 1초가 지나면 8개의 재우기 요청이 들어가는 거야?"

네, 들어갑니다. 다만 "쉬고 있는 깨어 있는 세션"과 "이미 잠든 세션"이 둘 다 남아 있을 때만입니다(`turnover.go`의 `tick`: `credit >= 1 && len(idle) > 0 && len(parked) > 0`).

- 앞의 재우기가 끝나기를 기다리지 않습니다. 다음 tick에는 다른 세션들에게 재우기를 보냅니다.
- 재우는 중인 세션은 "잠든 세션"으로 치지 않습니다. 그래서 잠든 세션이 초당 8개씩 깨워져 나가는데 초당 약 1.2개만 새로 채워지고, 약 10초 뒤에는 잠든 세션이 바닥납니다.
- 그 뒤로는 재우기가 하나 끝나야 교체 한 쌍을 내보낼 수 있습니다. 못 보낸 요청은 쌓이지 않고 버려집니다(`rate+1`까지만 보관).
- 이때 깨어 있지 않은 세션은 거의 다 재우기 줄에 서 있게 됩니다. 계산: (전체 − 깨어 있는 수) ÷ 완료 속도. C_turn96은 72 ÷ 1.16 = 62초(측정 p50 54초, p95 59초), C_turn24는 18 ÷ 1.22 = 15초(측정 14초, 15초), C_turn48은 36 ÷ 1.09 = 33초(persist 측정 35초, 37초). 세 실행 모두 맞습니다.

### Q29. (2026-11-19) "자원이 부족해서 재우고 깨우는데, 전부 깨워도 메모리에 다 올라가는 평가 환경이라면 잘못된 거 아닌가?"

절반은 맞습니다. 이번 C 단계는 "재우기·깨우기 한 번의 비용"은 재지만 "자원이 모자랄 때의 동작"은 재지 못합니다.

- 재지 못한 것: 깨어 있는 수(24개)는 자원이 모자라서가 아니라 부하 도구의 설정값으로 정해졌습니다. 깨우기가 "다른 Actor가 재워져 자리가 날 때까지" 기다리는 상황이 없었으므로, 깨우기 0.30초는 자리가 비어 있을 때의 값입니다.
- 여전히 유효한 것: 재울 때마다 쓰는 양, 재우기 한 건의 처리 시간, 올리기 창구의 한계(초당 약 1.2개)는 자원 여유와 관계없이 같은 경로를 탑니다.

### Q30. (2026-11-19) "자원이 풀로 사용되는 환경에서 재우기가 이 수준으로 밀리면 메모리 자원 기준 가용 가능한 에이전트 수가 크게 줄어들 수 있다는 것을 보여주는 거지. 이를 위한 평가 설계 해봐."

설계의 뼈대(아직 실행하지 않음, 스크립트 미작성):

- 근거가 되는 동작: sync 재우기에서 worker 용량은 올리기까지 끝난 뒤에 풀립니다(`src/substrate/cmd/ateapi/internal/controlapi/workflow_suspend.go`의 `ensureSuspendedFinalized`가 atelet의 Checkpoint 반환 뒤에 worker를 놓음). 메모리 내용은 0.3초 만에 dump되지만 "예약된 자리"는 재우기가 끝날 때까지 잡혀 있습니다. 소스를 읽은 것이고 실행 미확인.
- 계산 모형: 자리 K개, 일하는 시간 A, 쉬는 시간 I, 재우기가 자리를 잡고 있는 시간 S일 때 받을 수 있는 Agent 수는 K × (A+I) ÷ (A+S). 이상값(S=0) 대비 비율은 A ÷ (A+S).
- 실험: 용량을 작게 고정(K를 먼저 실측)하고, 모든 세션이 "일하고 → 재우고 → 쉬고 → 깨어나는" 반복을 하게 한 뒤 세션 수 N을 올립니다. 한 번에 한 요인만 바꾸는 네 갈래: 재우지 않음 / sync 기본 / async / sync + 업로드 한도 2Gi.
- 잴 것: 깨우기 요청부터 실제 시작까지의 대기, 용량 오류 재시도 수, 재우기 단계별 시간, worker의 예약량 시계열, cgroup `memory.stat`. 판정값은 "깨우기 대기 p95가 기준 안에 드는 최대 N".
- 먼저 확인할 것: K의 실제 값, `TimeToWake`가 용량 재시도 시간을 포함하는지, 대본에서 일하는 시간과 쉬는 시간을 정하는 방법.
