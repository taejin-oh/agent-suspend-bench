# 자리가 모자란 환경의 평가 (G 단계): 설계와 계획

작성일 2026-11-19. 이 문서는 `scripts/stage.sh`의 G 단계가 무엇을 왜 재는지, 결과를 어떻게 읽는지 설명합니다. 실행 방법은 `docs/handoff/HANDOFF.md`를 따릅니다(G 단계도 다른 단계와 같은 방식으로 돕니다).

## 1. 왜 필요한가

Linux 서버에서 돌린 C 단계(turnover)는 재우기 p50이 54초까지 늘었지만 깨우기는 0.30초였습니다. 이 결과만으로는 "재우기가 느려도 깨우기는 빠르다"로 읽힙니다. 그러나 그 실행에서는 **자리가 남아 있었습니다.** 깨어 있는 수는 자원이 모자라서가 아니라 부하 도구의 설정값(`agentsession_awake`)으로 정해졌고, worker의 용량은 제한하지 않았습니다.

재우기와 깨우기는 자원이 모자랄 때 쓰는 기능입니다. 그래서 자리가 꽉 찬 상태에서 재우기가 길어지면 무슨 일이 생기는지를 따로 재야 합니다.

## 2. 확인하려는 것

> 자리가 꽉 찬 환경에서는 재우기가 길어지는 만큼 자리가 묶이고, 같은 worker가 받을 수 있는 Agent 수가 줄어든다.

아직 가설입니다. 근거는 소스에서 읽은 동작이고 실행으로 확인한 것이 아닙니다.

- 재울 때 메모리 내용은 0.3초 안팎에 저장되고 프로세스는 사라집니다(`worker_checkpoint` 단계. 서버 C 단계의 p50 0.29~0.31초).
- 그러나 worker가 그 Actor에 내준 자리(예약 용량)는 재우기 전체가 끝난 뒤에 풀립니다. 제어부가 저장 단계의 반환을 받은 뒤에 worker를 놓기 때문입니다(`src/substrate/cmd/ateapi/internal/controlapi/workflow_suspend.go`의 `ensureSuspendedFinalized`).
- sync 방식의 저장 단계(`persist`)는 객체 저장소로 올리는 것까지 포함합니다(`src/substrate/cmd/atelet/main.go`의 `UPLOAD_MODE_IMMEDIATE` 분기). 올리기는 공유 한도(`--upload-memory-budget`, 기본 512 MiB)에서 자리를 받아야 시작하므로, 재우기가 몰리면 줄을 섭니다.

묶이는 것은 "예약된 자리"입니다. 실제로 쓰고 있는 메모리가 아니라, Substrate가 Actor의 메모리 한도만큼 worker 용량에서 떼어 둔 몫입니다. 결과를 말할 때 이 구분을 함께 적습니다.

## 3. 예상 계산

자리 K개, 일하는 시간 A, 쉬는 시간 I, 재우기가 자리를 잡고 있는 시간 S라고 하면 다음과 같습니다.

- 받을 수 있는 수 = K × (A + I) ÷ (A + S)
- 이상값(S = 0) 대비 비율 = A ÷ (A + S)

| 일하는 시간 A | 재우기 S | 이상값 대비 |
|---|---|---|
| 5초 | 1초 | 83% |
| 5초 | 5초 | 50% |
| 5초 | 54초 | 8% |

S는 고정값이 아닙니다. 재우기 요청이 올리기 한도에 가까워지면 줄이 생겨 급격히 늘어납니다. 서버의 B, C 단계에서 sync 재우기는 조건과 관계없이 초당 1.1~1.3개만 끝났습니다. 이 실험의 계산값과 측정값이 얼마나 맞는지가 확인 대상입니다.

## 4. 실험 구성

**자리를 작게 고정합니다.** worker를 1개만 두고 worker pod의 메모리를 5Gi로 제한합니다(substrate 배포 스크립트의 `--worker-memory`). Actor의 메모리 한도는 512Mi이므로 동시에 깨어 있을 수 있는 수는 9개 안팎이 됩니다. 정확한 K는 계산하지 않고 재우지 않는 실행에서 실측합니다.

세션들의 시작은 35초(한 바퀴의 길이)에 걸쳐 고르게 흩뿌립니다(`agentsession_phase_in=35`). 흩뿌리지 않으면 세션들이 같은 박자로 움직여, 재우기 시간과 관계없이 자리 다툼이 생깁니다(10절의 Mac 시험에서 확인).

**부하는 반복형입니다.** 대본 `workloads/capacity-cycle.yaml`의 모든 세션이 "깨어남 → 약 5초 일함 → 재움 → 약 30초 쉼"을 되풀이합니다. turnover 방식은 쓰지 않습니다. turnover는 처리 한계에 닿으면 목표 속도가 의미를 잃기 때문입니다(서버 C 단계의 세 실행이 같은 한계를 세 번 잰 것이었습니다).

**세션 수를 올리며 네 갈래를 비교합니다.** 갈래 사이에서 다른 것은 재우기 방식 하나뿐입니다.

| 갈래 | 실행 이름 | 설정 | 역할 |
|---|---|---|---|
| none | `G_none_n8`, `G_none_n16` | 재우지 않음 | K를 실측. 16개 실행은 자리가 모자라 실패가 나는 것이 정상 |
| sync | `G_sync_n8` ~ `n64` | 올리기까지 기다림, 한도 기본값 | 가설의 대상 |
| async | `G_async_n8` ~ `n64` | 로컬에 쓰면 끝 | 재우기가 짧을 때의 수용량 |
| 2g | `G_2g_n8` ~ `n64` | sync, 업로드 한도 2Gi | 줄이 원인인지 확인 |

세션 수는 8, 16, 32, 48, 64입니다. 계산상 재우기 요청은 각각 초당 약 0.2, 0.5, 0.9, 1.4, 1.8개이므로, 32개 근처에서 올리기 한도(초당 약 1.2개)에 닿습니다. 실행은 17개이고 각 4~5분입니다.

## 5. 재는 것

| 값 | 어디에 남는가 | 뜻 |
|---|---|---|
| 깨우기 시간 (`TimeToWake`) | `stats.json`, `summary.txt` | 첫 깨우기 요청부터 첫 응답까지. **자리가 없어 다시 시도한 시간을 포함**합니다(소스: `agentsession.go`의 설명) |
| 깨우기 실패 | 같은 곳 | 60초 동안 자리를 얻지 못한 횟수 (`agentsession_resume_retry_budget`의 기본값) |
| 자리 없음 거절 (`ResumeActor`의 실패 수) | 같은 곳 | 자리가 없어 거절된 깨우기 시도의 수. 시도마다 1건씩 기록되므로 깨우기 실패와 다릅니다. 오류 문구는 `no worker has room for the actor` |
| 재우기 시간과 단계별 시간 | `summary.txt`, `phases.txt` | S의 실제 값 |
| worker가 내준 자리 | `cap_10s.txt`의 `workers` 줄 | Actor 수, CPU, 메모리의 "쓴 양/용량". 10초 간격 |
| Actor 상태별 개수 | `cap_10s.txt`의 `actors` 줄 | 재우는 중(SUSPENDING)인 Actor가 몇 개인지 |
| kind 노드 cgroup의 메모리 내역 | `cap_10s.txt`의 `cgroup` 줄 | anon과 file을 구분. 예약과 실제 사용을 가르기 위함 |
| 디스크 통계 | `proc_1s.txt` | 기존 단계와 같음 |

## 6. 결과 읽기

`python3 scripts/capacity_report.py`가 `results/<HOST_LABEL>/CAPACITY.md`를 만듭니다. 갈래별로 "깨우기 기준을 지킨 최대 세션 수"가 한 줄씩 나옵니다.

- 기준은 깨우기 p95가 2.0초 이하이고 깨우기 실패가 0건인 것입니다. **2.0초는 이 저장소가 임의로 정한 값입니다.** 다른 값으로 보려면 둘째 인자로 줍니다(예: `python3 scripts/capacity_report.py results/company-server 5`).
- sync의 최대 세션 수가 async보다 작으면 가설과 맞습니다.
- 2g가 sync보다 크면 올리기 한도에서의 대기가 원인입니다.
- sync, async, 2g가 같으면 가설이 이 조건에서는 성립하지 않습니다. 이것도 결과입니다.
- `cap_10s.txt`에서 sync 실행의 재우는 중 Actor 수가 많고 그때 내준 메모리가 용량에 가까우면, 재우는 중인 Actor가 자리를 잡고 있다는 직접 증거입니다.

G 단계에서는 `FAILURES` 판정이 나오는 것이 정상입니다. 자리가 없어 거절된 깨우기 시도가 실패로 집계되기 때문입니다. 그래서 G 단계는 실패 판정이 나와도 멈추지 않고 다음 실행으로 넘어갑니다(실패한 실행은 한 번 더 돌린 뒤 넘어갑니다).

## 7. 실행 계획

| 순서 | 하는 일 | 소요 |
|---|---|---|
| 1 | 저장소를 최신으로 받음 (`git pull`) | 1분 |
| 2 | `scripts/stage.sh status`의 NEXT를 따라 G 단계 실행 | 약 2시간 (실패한 실행의 재실행 포함 시 최대 3시간) |
| 3 | `python3 scripts/report.py`, `python3 scripts/capacity_report.py` | 1분 |
| 4 | `CAPACITY.md`의 요약 절을 그대로 보고 | |

E, F 단계를 아직 돌리지 않았다면 G보다 먼저 돕니다(status가 순서대로 안내합니다). E와 F는 자리가 남는 환경에서 같은 두 요인(async, 업로드 한도)을 보는 단계라서 G의 결과와 나란히 놓고 읽습니다.

## 8. 이 평가로 말할 수 없는 것

- 운영 환경의 수치가 아닙니다. kind 노드 하나에 객체 저장소가 같은 디스크에 있는 구성입니다.
- 올리기 한도는 설정값입니다. "Substrate의 한계"가 아니라 "기본 설정에서의 동작"입니다.
- async는 올리기가 끝나기 전에 서버가 죽으면 snapshot을 잃습니다(substrate 문서 `docs/reference/api-guide.md`). 수용량과 안전성의 맞교환입니다.
- 대본은 가상 부하입니다. 일하는 시간 5초와 쉬는 시간 30초는 이 저장소가 정한 값이고 실제 Agent의 값이 아닙니다.
- 조건마다 1회 실행입니다. 흔들림은 재지 않았습니다.
- 깨우기 기준 2.0초는 임의의 값입니다.

## 9. 확인된 것과 확인되지 않은 것

| 항목 | 상태 |
|---|---|
| 대본 `capacity-cycle.yaml`이 substrate의 검사를 통과 | 확인 (`boomer-worker --check-agentsession-script`) |
| `TimeToWake`가 자리 재시도 시간을 포함 | 소스에서 확인 |
| worker 메모리를 제한하면 worker가 보고하는 용량이 줄어듦 | Mac에서 실행으로 확인 (10절) |
| 수집 스크립트와 `capacity_report.py`가 끝까지 돎 | Mac에서 실행으로 확인 (10절) |
| 재우는 동안 자리가 잡혀 있음 | 소스에서 읽음. 이 평가가 실행으로 확인할 대상 |
| G 단계 전체(17개 실행) | Linux 서버에서 처음 돌림 |

## 10. Mac에서의 시험 실행

(아래는 스크립트가 끝까지 도는지 확인하려고 작은 규모로 돌린 것입니다. 결론을 내기 위한 실행이 아닙니다.)

조건: Mac(OrbStack, 메모리 8 GB)의 kind 노드, worker 메모리 1536Mi, Actor 512Mi, 세션 시작을 15초에 걸쳐 흩뿌림. 조건마다 1회.

| 확인한 것 | 결과 |
|---|---|
| worker 메모리 제한이 용량으로 반영되는가 | worker가 보고한 메모리 용량 1472 MiB. 재우지 않는 실행(세션 4개)에서 동시에 자리를 받은 Actor는 최대 2개 |
| 자리가 모자랄 때 깨우기가 어떻게 기록되는가 | sync, 세션 6개: 깨우기 26회 모두 성공, p50 0.94초, p95 12초. 자리 없음 거절 93건(`no worker has room for the actor`). 재우기 p50 0.94초 |
| 새 수집 항목 | `cap_10s.txt`에 worker가 내준 자리, Actor 상태별 개수, cgroup의 anon/file이 기록됨 |

이 시험에서 고친 것이 세 가지 있습니다.

- **worker 메모리가 노드의 여유보다 크면 배포가 실패합니다.** 처음에 3Gi를 줬을 때 pod가 `Insufficient memory`로 배치되지 못했습니다. 서버에서 같은 일이 생기면 `site.env`에 `export ASB_CAP_WORKER_MEMORY=<더 작은 값>`을 넣습니다. 값을 바꾸면 K가 달라지므로 보고에 함께 적습니다.
- **실패한 배포가 남긴 pod 때문에 다음 실행이 멈추던 것을 고쳤습니다.** 배포를 바꿔야 하는 실행은 먼저 새로 배포합니다(`scripts/stage.sh`의 `do_run`).
- **세션 시작을 한 바퀴 길이(35초)에 걸쳐 흩뿌리도록 바꿨습니다.** 위 시험은 15초였고, 세션 6개가 자리 2개에 몰려 p95가 12초까지 늘었습니다. 이 값은 재우기 시간이 아니라 몰림 때문이므로 가설의 근거로 쓰지 않습니다.

async 실행은 이 시험에서 돌지 않았습니다. 시험용 단계(X)는 실패 판정이 두 번 나오면 끝나기 때문입니다. G 단계는 계속 진행하도록 돼 있고, 그 분기는 Mac에서 돌려 보지 않았습니다.
