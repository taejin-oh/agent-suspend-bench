안녕하세요. 오늘은 AI Agent를 대량으로 운영할 때 스토리지에 어떤 부담이 생기는지, 그것을 어떻게 측정할 수 있는지를 말씀드리겠습니다. 순서는 네 부분입니다. 무엇을 확인하려 했는지, 측정에 쓴 Agent Substrate가 무엇인지, 작은 환경에서 직접 측정한 결과, 그리고 본 검증을 어떻게 진행할지입니다. 오늘 보여드리는 수치는 모두 직접 측정한 원본 데이터에서 가져왔고, 공식 문서에서 인용한 수치는 따로 표시했습니다.

확인하려는 것

다수의 Agent가 잠들고 깨기를 반복하면
스토리지에 문제가 생기는가

Agent Substrate는 Kubernetes용 오픈소스 런타임이다. 쉬는 Agent의 메모리와 파일을 디스크에 저장하고 자리에서 내린다(재우기, suspend). 요청이 오면 복원한다(깨우기, resume). 재울 때마다 스토리지에 쓰기가 생긴다.

여기서 문제란 실패가 생기거나, 재우기와 깨우기가 크게 느려지거나, 필요한 쓰기 속도와 용량이 장치의 한계를 넘는 것을 말한다.

작은 환경에서 먼저 확인한 세 가지 (실제 규모의 검증은 Linux 서버에서 한다)

질문 1

설치되고, 재우기와 깨우기가 끝까지 동작하는가

질문 2

실제 Agent를 돌리지 않고 이 부하를 만들 수 있는가

질문 3

부담과 지연을 수치로 측정할 수 있는가

확인하려는 것은 한 문장입니다. 많은 Agent가 깨어났다 잠들기를 반복하면 스토리지에 문제가 생기는가. Agent Substrate는 쉬는 Agent를 통째로 저장해서 자리에서 내리는 런타임입니다. 이 동작을 재우기, 다시 올리는 동작을 깨우기라고 부르겠습니다. 재울 때마다 스토리지에 쓰기가 생기기 때문에, Agent가 많아지면 이 쓰기가 감당할 수 있는 수준인지가 궁금해집니다. 여기서 문제라고 하는 것은 세 가지입니다. 실패가 생기는 것, 재우기와 깨우기가 크게 느려지는 것, 그리고 필요한 쓰기 속도나 용량이 장치의 한계를 넘는 것입니다. 실제 Agent를 대량으로 돌려 보면 가장 확실하지만, LLM을 대량으로 호출하면 비용이 크고 결과도 매번 달라집니다. 그래서 실제 규모의 검증에 앞서 작은 환경에서 세 가지를 먼저 확인했습니다. 오늘 발표는 이 세 질문에 대한 답이고, 맨 위의 본 질문은 서버 검증에서 답할 예정입니다.

초

지연과 쓰기량이 측정된다

동시에 재우자 재우기 시간(중앙값)이 약 11배가 됐다. 주된 원인이 디스크가 아닌 설정임을 찾았다. 1회 쓰기는 약 320 MiB.

본 질문의 답은 아직 없다. 가상 머신 1대, 가상 Agent 12개 규모의 결과다. Linux 서버에서 규모를 키워 확인한다.

출처: 자체 측정 (2026년 11월). 횟수는 부하 실행 8회의 합계, 시간은 업로드까지 기다리는 방식으로 잰 값

결론부터 말씀드립니다. 첫째 질문의 답은 예입니다. 소스 수정 없이 설치됐고, 재우기와 깨우기 요청 2,046회가 실패 없이 끝났습니다. 상태가 이어지는지는 예제 하나로 세 번 확인했습니다. 둘째 질문도 예입니다. 다만 쓰기 경로에 한해서입니다. LLM을 한 번도 호출하지 않고 시나리오 파일만으로 가상 Agent 12개를 재우고 깨웠습니다. 이 가상 부하가 실제 Agent와 얼마나 닮았는지는 검증하지 못했습니다. 셋째 질문도 예입니다. 여러 개를 동시에 재우면 재우기 한 번에 걸리는 시간이 늘어나는 것이 측정됐습니다. 하나만 돌릴 때 중앙값 0.83초이던 것이, 계속 바꿔 가며 재우고 깨우는 부하에서는 8.9초가 됐습니다. 이 값은 저장본을 원격 스토리지에 올리는 것까지 기다리는 방식으로 잰 값입니다. 소스에서 업로드를 제한하는 설정을 찾았고, 그 설정을 올리자 2.3초가 됐으며 되돌리자 다시 느려졌습니다. 이 부분은 뒤에서 자세히 보겠습니다. 중요한 점은, 스토리지에 문제가 생기는가 하는 본 질문에는 아직 답하지 않았다는 것입니다. 지금 결과는 가상 머신 한 대에서 얻은 값입니다.

AGENT SUBSTRATE란

쉬는 Agent를 디스크로 내려, 적은 자리로 많은 Agent를 돌린다

Agent는 대부분의 시간을 모델·도구·사람의 응답을 기다리며 보낸다. 그 시간 동안 자리를 비우게 하는 것이 핵심이다. Kubernetes 위에서 동작하는 오픈소스다 (Apache-2.0).

ACTOR

Agent 인스턴스 하나

메모리와 파일 상태를 가진 작업 단위. 수가 매우 많고 대부분 쉬고 있다.

WORKER

미리 띄워 둔 빈 자리

격리 실행 환경(sandbox)을 가진 Kubernetes 실행 단위(pod). Actor보다 훨씬 적게 둔다.

SNAPSHOT

재울 때 남기는 저장본

메모리와 파일 상태 전체. checkpoint라고도 한다. 오늘은 이것을 쓰는 부담을 다룬다.

공식 문서에 제시된 수치 (이번에 측정한 값이 아님): 컨테이너 대비 10배 밀도 · 깨우기 500ms 미만 · 초당 500회 이상 깨우기

출처: github.com/agent-substrate/substrate 의 README, docs/concepts/architecture.md

Agent Substrate는 Kubernetes 위에서 도는 오픈소스 런타임입니다. 핵심 아이디어는 단순합니다. Agent는 대부분의 시간을 모델이나 도구, 사람의 응답을 기다리며 보냅니다. 그 시간 동안은 상태를 통째로 저장해서 자리에서 내리고, 요청이 오면 빈 자리에 다시 올립니다. 그래서 많은 Agent를 적은 자리에 겹쳐 올릴 수 있습니다. 용어 세 개만 기억하시면 됩니다. Actor는 Agent 인스턴스 하나입니다. Worker는 미리 띄워 둔 빈 자리입니다. Snapshot은 재울 때 남기는 저장본으로, 메모리와 파일 상태 전체가 들어 있습니다. 이 프로젝트를 고른 이유는, 재우기와 깨우기를 전제로 설계된 공개 런타임이라 우리가 보려는 부하를 그대로 만들 수 있기 때문입니다. 아래 수치는 공식 문서에 제시된 것이고 제가 측정한 값이 아닙니다. 해당 문서에는 측정 조건이 함께 적혀 있지 않아서, 오늘 제 측정값과 직접 비교할 수는 없습니다.

동작 방식

재울 때마다 상태 전체를 두 곳에 쓴다

먼저 노드의 로컬 디스크에, 그다음 압축해서 객체 스토리지에. 주황색 두 곳이 쓰기가 생기는 지점이다.

1. 실행 중

Actor가 worker 안의 sandbox에서 동작한다.

2. 재우기 요청

sandbox를 멈추고 상태를 덤프한다.

3. 로컬 디스크

snapshot을 노드에 쓴다. sandbox는 정리된다.

4. 객체 스토리지

zstd로 압축해 올린다. 최신 것만 둔다.

깨우기 (반대 방향)

요청이 오면 빈 worker에 snapshot을 복원한다. 같은 노드에 로컬 사본이 있으면 그것을 쓰고, 없으면 객체 스토리지에서 내려받는다. 재우기가 끝나야 다시 깨울 수 있다.

재우기 방식 두 가지

sync는 4번 업로드가 끝나야 재우기가 완료된다. 기본값인 async는 3번까지만 기다리고 업로드는 뒤에 한다. 이번에는 업로드 부담까지 보이도록 sync로 쟀다.

출처: Substrate 문서 docs/concepts/architecture.md, 소스 internal/objectstoreplugin

왜 스토리지가 문제가 될 수 있는지 보여주는 그림입니다. Actor 하나를 재울 때 메모리와 파일 상태가 먼저 노드의 로컬 디스크에 쓰입니다. 이것을 덤프라고 부르겠습니다. 그다음 zstd로 압축돼서 객체 스토리지로 올라갑니다. 즉 재우기 한 번에 쓰기가 두 곳에서 생깁니다. 깨우기는 반대 방향입니다. 같은 노드에 로컬 사본이 남아 있으면 그것으로 복원하고, 없으면 객체 스토리지에서 내려받습니다. 한 가지 더, 재우기가 끝나야 그 Actor를 다시 깨울 수 있습니다. 그래서 재우기가 길어지면 그 사이에 온 요청이 기다리게 됩니다. 재우기 방식은 둘입니다. sync는 업로드까지 기다립니다. 기본값인 async는 로컬 디스크에 쓰는 것까지만 기다리고, 업로드는 기본 5분 뒤에 따로 합니다. 이번에는 업로드 부담이 재우기 시간에 그대로 드러나도록 sync로 측정했습니다. 기본값이 아닌 방식으로 쟀다는 점은 결과를 보실 때 기억해 주시기 바랍니다.

검증 방법

Agent는 모사, snapshot 쓰기는 실제

LLM은 호출하지 않는다. 시나리오대로 자원을 쓰는 가상 Actor를 실제 Agent Substrate 위에서 재우고 깨운다. 쓰기 경로는 실제이고, 크기와 압축률은 시나리오가 정한다.

가상 ACTOR

시나리오 파일대로 동작

Substrate에 포함된 부하 도구를 썼다. 단계마다 메모리 채우기, 디스크 쓰기, CPU 사용, 대기 시간을 지정한다.

이번 시나리오: 5단계, 메모리 64 MiB(무작위 데이터), 디스크 약 24 MiB

환경

가상 머신 1대의 Kubernetes

시험용 Kubernetes(kind)에 Substrate를 소스 수정 없이 설치했다. S3 호환 객체 스토리지(rustfs)도 같은 클러스터 안에 둔다.

worker 4개, 격리 방식은 gVisor(오픈소스 sandbox)

부하 두 가지

일반 부하와 교체 부하

일반. 각 Actor가 5단계를 반복하고, 단계가 끝날 때마다 재웠다가 깨운다. 1개와 4개로 실행.

교체(turnover). 12개 중 3개만 깨어 있게 둔다. 1초에 한 번, 깨어 있는 하나를 재우고 자던 하나를 깨운다.

측정 환경: Apple M4의 가상 머신(10 vCPU, 메모리 8 GB). 쓰기는 모두 데이터 디스크 1개에 합쳐진다. Substrate commit d283af4e

방법의 핵심은, Agent는 모사하지만 snapshot 쓰기는 실제로 일어난다는 점입니다. Substrate에 포함된 부하 도구가 시나리오 파일대로 메모리와 디스크를 쓰는 가상 Actor를 만듭니다. 이번 시나리오는 다섯 단계이고, 메모리 64 MiB를 무작위 데이터로 채우고 디스크에 약 24 MiB를 씁니다. 이걸 재울 때는 실제로 메모리가 디스크에 쓰이고 객체 스토리지로 올라갑니다. 다만 Actor의 크기와 데이터의 압축률은 시나리오가 정한 값이라 실제 Agent와 다를 수 있습니다. 환경은 가상 머신 한 대 안의 시험용 Kubernetes입니다. 객체 스토리지도 같은 클러스터 안에 두었습니다. 부하는 두 가지입니다. 일반 부하는 각 Actor가 단계를 하나 끝낼 때마다 잠드는 방식으로, Actor 1개와 4개로 각각 돌렸습니다. 교체 부하가 우리가 보려는 상황입니다. 12개 중 3개만 깨어 있게 두고, 1초에 한 번씩 깨어 있는 하나를 재우고 자던 하나를 깨웁니다.

직접 확인한 것

가상 머신 1대에서 설치부터 부하까지 실패 없이 끝났다

#확인한 것결과
1Kubernetes 클러스터 생성성공
2Agent Substrate 설치소스 수정 없이 설치, 구성 요소 모두 정상 기동
3worker 기동 (gVisor sandbox)정상. Linux 자원 격리 기능인 cgroup v2가 필요하다
4재우기/깨우기 3회 반복 (예제 Actor 1개)상태 보존: 메모리, 파일, 루트 파일시스템에 둔 카운터가 1 → 4로 이어짐
5가상 Actor와 부하 도구 배포성공
6일반 부하: Actor 1개, 4개 (각 2분)재우기 129회, 깨우기 125회, 실패 0건
7교체 부하: 12개 중 3개 깨어 있음 (5분)재우기 176회(시작할 때 12회 포함), 깨우기 176회, 실패 0건
84개 부하와 교체 부하를 한 번 더 실행같은 경향 (교체 부하의 재우기 중앙값 9.8초와 8.9초)
9업로드 메모리 한도를 올려 같은 부하 실행실패 0건, 재우기 중앙값 8.9초 → 2.3초. 되돌리자 다시 11초

출처: 자체 측정 (2026년 11월). 실패 수는 부하 도구 기준이며, 깨우기는 도구가 최대 1분까지 다시 시도한다

직접 확인한 것 아홉 가지입니다. 클러스터 생성, Substrate 설치, worker 기동, 재우기와 깨우기의 상태 보존, 부하 도구 배포, 그리고 부하 두 종류입니다. 4번이 가장 기본적인 확인입니다. 예제 Actor 하나를 세 번 재웠다 깨웠는데, 메모리와 파일, 루트 파일시스템에 각각 둔 카운터가 1, 2, 3, 4로 이어졌습니다. 재웠다 깨워도 초기화되지 않고 상태가 보존된다는 뜻입니다. 이 예제 Actor는 메모리를 수 MiB만 쓰고, 재우기에 0.25초에서 0.32초가 걸렸습니다. 실패 수는 부하 도구가 본 기준이고, 깨우기는 도구가 최대 1분까지 다시 시도합니다. 4개 부하와 교체 부하는 두 차례 돌렸고 경향이 같았습니다. 1개 기준 실행은 한 번입니다. 마지막 9번은 재우기가 느려지는 원인을 확인하려고 설정 하나를 바꿔 다시 돌린 것으로, 뒤에서 따로 말씀드립니다. Substrate 소스는 수정하지 않았습니다.

실제 환경과 다른 점

디스크. 가상 디스크 1개에 모든 쓰기가 합쳐졌다.

노드. 1개뿐이라 객체 스토리지에서 내려받아 깨우는 경로는 거의 쓰이지 않았다.

데이터. 무작위 데이터로 채웠고 압축이 거의 되지 않았다.

보지 않은 것

장치의 한계. 디스크가 포화되는 지점까지 가지 못했다.

쓰기 수명과 읽기 부하. 측정하지 않았다.

반복. 1개 기준 실행과 한도를 올린 실행은 한 번씩만 했다.

절대값이 아니라 경향만 본다. 이 수치는 서버의 성능을 예측하지 않는다. 공식 문서의 수치와도 조건이 달라 직접 비교할 수 없다.
이 결과로는 알 수 없는 것을 분명히 해 둡니다. 첫째, 아직 실행하지 않은 것입니다. Linux 서버에서는 한 번도 돌리지 않았고, 12개를 넘는 규모, 더 큰 Actor, 기본값인 async 방식, 그리고 Substrate가 지원하는 또 하나의 격리 방식인 microVM도 해 보지 않았습니다. 둘째, 실제 환경과 다른 점입니다. 가상 디스크 하나에 모든 쓰기가 섞였고, 노드가 하나였고, 메모리를 무작위 데이터로 채웠습니다. 가상 디스크의 사용률은 실제 장치의 여유를 그대로 말해 주지 않습니다. 셋째, 보지 않은 것입니다. 디스크가 포화되는 지점까지 가지 못했기 때문에 스토리지 장치의 한계는 여전히 모릅니다. 쓰기 수명과 읽기 부하도 보지 않았습니다. 그래서 오늘 보여드린 절대값은 서버에서 어떤 값이 나올지 알려주지 않습니다. 공식 문서의 깨우기 500ms 미만이라는 수치와 비교하면, 겹침이 없을 때 제 측정값은 중앙값 0.14초였습니다. 하지만 공식 수치의 측정 조건이 문서에 없어서 직접 비교할 수는 없습니다.

재우기 빈도와 snapshot 크기를 올리며 한계 지점을 찾는다

로컬 디스크 쓰기 ≈ 초당 재우기 횟수 × snapshot 크기
객체 스토리지 쓰기 ≈ 초당 재우기 횟수 × 압축 후 크기
이번 값을 넣으면 0.72회 × (157 + 150) MiB ≈ 221 MiB/s. 디스크에서 잰 값은 231 MiB/s였다.

출처: 자체 측정 (2026년 11월). 디스크에서 잰 값에는 시나리오 자체의 디스크 쓰기도 들어 있다. 점유량은 Actor 수에 비례한다

그러면 서버에서 무엇을 볼지 말씀드리겠습니다. 쓰기 속도는 두 식으로 어림할 수 있습니다. 로컬 디스크 쓰기는 초당 재우기 횟수에 snapshot 크기를 곱한 값이고, 객체 스토리지 쓰기는 초당 재우기 횟수에 압축 후 크기를 곱한 값입니다. 이번 값을 넣으면 합쳐서 초당 221 MiB가 나오고, 디스크에서 실제로 잰 값은 231 MiB였습니다. 그래서 쓰기 속도를 정하는 것은 재우기 빈도와 snapshot 크기이고, 점유량은 Actor 수에 비례합니다. 예를 들어 snapshot이 1 GiB이고 초당 10회 재운다면 로컬과 객체 스토리지에 각각 초당 약 10 GiB가 필요합니다. 이것은 계산값이고 측정한 값은 아닙니다. 서버에서는 왼쪽 표의 값을 단계적으로 올립니다. 볼 지표는 다섯 가지입니다. 지연이 기준값의 몇 배가 되는지, 실패가 어디서 처음 생기는지, 그때 어떤 자원이 한계에 가까운지, 덤프와 업로드 중 어느 구간이 늘어나는지, 그리고 스토리지 점유량이 얼마나 느는지입니다.
