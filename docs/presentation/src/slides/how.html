동작 방식

재울 때마다 상태 전체를 두 곳에 쓴다

먼저 노드의 로컬 디스크에, 그다음 압축해서 객체 스토리지에. 주황색 두 곳이 쓰기가 생기는 지점이다.

1. 실행 중

Actor가 worker 안의 sandbox에서 동작한다.

2. 재우기 요청

sandbox를 멈추고 상태를 덤프한다.

3. 로컬 디스크

snapshot을 노드에 쓴다. sandbox는 정리된다.

4. 객체 스토리지

zstd로 압축해 올린다. 최신 것만 둔다.

깨우기 (반대 방향)

요청이 오면 빈 worker에 snapshot을 복원한다. 같은 노드에 로컬 사본이 있으면 그것을 쓰고, 없으면 객체 스토리지에서 내려받는다. 재우기가 끝나야 다시 깨울 수 있다.

재우기 방식 두 가지

sync는 4번 업로드가 끝나야 재우기가 완료된다. 기본값인 async는 3번까지만 기다리고 업로드는 뒤에 한다. 이번에는 업로드 부담까지 보이도록 sync로 쟀다.

왜 스토리지가 문제가 될 수 있는지 보여주는 그림입니다. Actor 하나를 재울 때 메모리와 파일 상태가 먼저 노드의 로컬 디스크에 쓰입니다. 이것을 덤프라고 부르겠습니다. 그다음 zstd로 압축돼서 객체 스토리지로 올라갑니다. 즉 재우기 한 번에 쓰기가 두 곳에서 생깁니다. 깨우기는 반대 방향입니다. 같은 노드에 로컬 사본이 남아 있으면 그것으로 복원하고, 없으면 객체 스토리지에서 내려받습니다. 한 가지 더, 재우기가 끝나야 그 Actor를 다시 깨울 수 있습니다. 그래서 재우기가 길어지면 그 사이에 온 요청이 기다리게 됩니다. 재우기 방식은 둘입니다. sync는 업로드까지 기다립니다. 기본값인 async는 로컬 디스크에 쓰는 것까지만 기다리고, 업로드는 기본 5분 뒤에 따로 합니다. 이번에는 업로드 부담이 재우기 시간에 그대로 드러나도록 sync로 측정했습니다. 기본값이 아닌 방식으로 쟀다는 점은 결과를 보실 때 기억해 주시기 바랍니다.
