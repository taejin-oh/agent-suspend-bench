정리와 다음 단계

다음 단계: Linux 서버에서 규모를 키워 한계를 찾는다

1 · 먼저

서버에서 관문 통과

Linux 서버에서 점검, 설치, 상태 보존 확인까지 실행한다. 환경 문제가 있으면 여기서 드러난다.

2 · 그다음

기준값을 잡고 규모 확대

이번과 같은 조건으로 기준값을 잡는다. 그 뒤 재우기 빈도와 Actor 크기를 올리고, async 방식도 측정한다.

3 · 설정과 장치를 나눠 보기

장치의 한계를 따로 잰다

업로드 메모리 한도 같은 설정을 먼저 맞춘다. 그다음 snapshot 전용 디스크와 별도 객체 스토리지를 두어 장치의 한계를 잰다.

오늘의 요점

실제 Agent 없이 이 부하를 만들 수 있고, 지연과 쓰기량이 측정된다. 이번에 먼저 닿은 한계는 디스크가 아니라 설정이었다. 스토리지가 한계에 닿는 지점은 서버 검증에서 확인한다.

재현 스크립트와 원본 측정 데이터는 Git 리포지토리로 정리해 두었다

정리하겠습니다. 다음 단계는 세 가지입니다. 먼저 Linux 서버에서 0번부터 4번까지 돌려 관문을 통과시킵니다. 그다음 이번과 같은 조건으로 한 번 돌려 기준값을 잡고, 재우기 빈도와 Actor 크기를 올립니다. 기본값인 async 방식도 이때 측정합니다. 마지막으로 설정과 장치를 나눠서 봅니다. 업로드 메모리 한도 같은 설정을 먼저 맞추고, 그다음 snapshot 전용 디스크와 별도의 객체 스토리지를 두어서 장치 자체의 한계를 잽니다. 오늘의 요점은 세 가지입니다. 실제 Agent 없이도 이 부하를 만들 수 있고 지연과 쓰기량이 측정된다는 것, 이번 환경에서 먼저 닿은 한계는 디스크가 아니라 소프트웨어 설정이었다는 것, 그리고 스토리지가 한계에 닿는 지점은 서버 검증에서 확인한다는 것입니다. 재현 스크립트와 원본 측정 데이터는 Git 리포지토리로 정리해 두었습니다. 감사합니다.
