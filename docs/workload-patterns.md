# 워크로드 패턴 가이드

Agent Substrate의 부하 도구로 만들 수 있는 워크로드 패턴을 정리한 문서입니다. 패턴을 어떻게 조절하는지, 패턴마다 무엇을 흉내 내고 무엇을 못 흉내 내는지, 결과를 어디까지 믿을 수 있는지를 다룹니다.

근거는 세 단계로 표시했습니다.

- **(실행)** 이 저장소의 스크립트로 Mac(OrbStack VM, 10 vCPU / 8 GB)에서 직접 돌려 확인한 것
- **(소스)** substrate 소스 코드에서 읽어 확인했지만 돌려 보지는 않은 것 (commit `d283af4e`)
- **(문서)** substrate 문서에만 있고 코드로 확인하지 않은 것

## 1. 요약

- 패턴은 세 층으로 조절합니다. 배포할 때 정하는 값(worker 수, Actor 메모리, 대본), 실행할 때 정하는 값(세션 수, 교체 속도, 재우기 방식 등), 대본 안에 쓰는 값(단계, 대기 시간, 메모리·디스크·CPU 사용량)입니다.
- "다수 Agent가 활성/비활성을 반복"하는 상황은 **turnover(교체) 모드**가 가장 가깝습니다. 스토리지 부담을 보려면 여기에 대본의 메모리 크기와 교체 속도를 키웁니다.
- 모든 패턴은 "앞 요청이 끝나야 다음 요청을 보내는" 방식입니다. 시스템이 느려지면 요청도 같이 줄어듭니다. 그래서 목표 속도와 실제 처리 속도를 반드시 같이 봐야 합니다.
- 가상 Agent가 쓰는 데이터는 무작위 바이트라 압축이 거의 되지 않습니다(측정값 약 1~5%). 실제 Agent보다 업로드와 저장 공간에 불리한 조건입니다.
- 같은 조건을 다시 돌려도 수치가 꽤 움직입니다. 교체 부하의 재우기 중앙값은 기본 설정에서 8.9 / 9.8 / 11초, 업로드 한도를 올린 설정에서 2.3 / 3.8초였습니다. 한 번의 실행을 결론으로 쓰면 안 됩니다.

## 2. 패턴 한눈에 보기

부하 도구는 "유저 클래스"를 하나 골라 배포합니다. 클래스마다 가상 사용자가 하는 일이 다릅니다.

| 패턴 (유저 클래스) | 가상 사용자 하나가 하는 일 | 무엇을 보려는 패턴인가 | 이 저장소 스크립트 | 근거 |
|---|---|---|---|---|
| `agentsession` 일반 모드 | Actor 1개로 대본을 한 단계씩 실행. 단계 사이에는 재워 두고, 다음 단계에서 깨움 | 코딩 Agent 여러 개가 각자 일하는 상황 | 지원 | 실행 |
| `agentsession` turnover 모드 | N개를 만들어 모두 재운 뒤 K개만 깨워 두고, 초당 R개씩 깨어 있는 것과 자는 것을 교체 | 많은 Agent 중 일부만 활성인 상태에서 계속 바뀌는 상황 | 지원 | 실행 |
| `glutton` | 깨우기 → (메모리 채우기) → ping → 재우기 → 잠깐 대기를 반복 | 재우기/깨우기 자체의 비용 (플랫폼 기준선) | 미지원 (배포 옵션만 바꾸면 가능) | 소스 |
| `sweperf` | 녹화된 SWE-Perf 작업을 4번에 나눠 실행하고, 사이마다 재웠다 깨움 | 실제 코딩 작업에 가까운 CPU·디스크 사용 | 미지원 | 소스 |
| `resumepaused` | Actor에 요청은 보내지 않고, 정해진 속도로 깨우기/재우기만 호출 | 제어부(API 서버)가 초당 몇 번을 감당하는가 | 미지원 | 소스 |
| `spawn`, `durdir`, `ate_env` 등 | 일괄 생성 시간, 영속 디렉터리, 명령 실행 | 특정 기능 | 미지원 | 소스 |

이 저장소의 `scripts/05_deploy_benchmark.sh`는 `agentsession`으로 고정해 배포합니다. 다른 클래스를 쓰려면 substrate의 `benchmarking/locust/deploy.sh --user-class <이름>`을 직접 호출해야 합니다.

## 3. 조절하는 방법

### 3.1 배포할 때 정하는 값

`scripts/05_deploy_benchmark.sh [대본.yaml]`로 정합니다. 환경 변수로 줄 수 있는 것은 `WORKER_COUNT`, `ACTOR_MEMORY`, `SKIP_BUILD`뿐입니다. 격리 방식과 Actor CPU는 스크립트를 고치거나 substrate의 `deploy_locust.sh`를 직접 호출해야 합니다. 값을 바꾸면 다시 배포해야 합니다. Actor 템플릿은 한번 만들면 바꿀 수 없기 때문입니다(소스).

| 무엇 | 어떻게 | 기본 | 영향 | 근거 |
|---|---|---|---|---|
| worker 수 | `WORKER_COUNT=N` | 4 | Actor를 받는 worker pod의 수. worker 하나가 여러 Actor를 받으므로(기본 최대 1000개) 동시 활성 수의 상한은 아님. 상한은 Actor의 CPU·메모리 한도를 worker 용량에 예약하는 방식으로 정해짐 | 실행 / 소스 |
| Actor 메모리 한도 | `ACTOR_MEMORY=1536Mi` | 512Mi | 대본의 `min_actor_memory` 이상이어야 함. 클수록 snapshot에 딸려 들어가는 페이지 캐시도 커진다고 함 | 512Mi만 실행 / 소스 |
| 대본 | 인자로 YAML 파일 | `workloads/smoke-5step.yaml` | Agent가 하는 일 전체 (4절) | 실행 |
| 격리 방식 | substrate `--sandbox-class gvisor\|microvm` | gvisor | microvm은 `/dev/kvm` 필요 | gvisor만 실행 |
| Actor CPU 한도 | substrate `--actor-cpu` | 1 | worker 하나가 받을 수 있는 Actor 수에 영향 | 소스 |
| 업로드 메모리 한도 | atelet DaemonSet의 `--upload-memory-budget` | 512Mi | 동시에 올릴 수 있는 업로드 수. sync 재우기 시간에 큰 영향 (README "원인 확인") | 실행 |

### 3.2 실행할 때 정하는 값

`scripts/06_run_load.sh <이름> <세션 수> <초> [key=value ...]`로 줍니다. key는 부하 도구 옵션 이름에서 `--`를 떼고 `-`를 `_`로 바꾼 것입니다.

| 무엇 | key | 기본 | 뜻 | 근거 |
|---|---|---|---|---|
| 세션(Actor) 수 | 둘째 인자 | 필수 | 가상 사용자 수. 각자 Actor 1개를 가짐 | 실행 |
| 실행 시간 | 셋째 인자 | 필수 | 초. turnover는 등록과 1분 대기가 먼저 있으므로 5분 이상 권장 | 실행 |
| 재우기 방식 | `lifecycle_mode` | `async` | `sync`: 객체 스토리지 업로드까지 기다림. `async`: 로컬 디스크에 쓰면 끝, 업로드는 나중(기본 5분 뒤). `none`: 재우지 않음 | sync·async 실행 |
| 깨우기 방식 | `resume_mode` | `explicit` | `explicit`: 깨우기 API를 먼저 호출. `implicit`: 요청을 그냥 보내고 라우터가 깨우게 함 | 둘 다 실행 |
| 대기 시간 배율 | `agentsession_think_scale` | 1.0 | 대본의 단계 사이 대기 시간에 곱함. 항상 ±20% 흔들림이 붙음 | 실행 |
| 깨어 있는 수 | `agentsession_awake` | 0 | 1 이상이면 turnover 모드 | 실행 |
| 초당 교체 수 | `target_rps` | 0 | turnover에서 1초에 몇 쌍을 교체할지. 목표값이지 보장값이 아님 | 실행 |
| 시작 분산 | `agentsession_phase_in` | 0 | 세션들의 시작을 이 초 범위 안에 흩뿌림. 안 주면 모두 같은 박자로 움직임 | 소스 |
| 깨우기 재시도 한도 | `agentsession_resume_retry_budget` | 60 | 빈 worker가 없을 때 깨우기를 몇 초까지 다시 시도할지 | 소스 |
| 일부 단계만 재우기 | `agentsession_snapshot_steps` | 없음 | 적은 단계 뒤에만 재움. turnover와 함께 못 씀 | 소스 |
| 세션 시작 속도 | 환경 변수 `SPAWN_RATE` | 1 | 초당 몇 세션씩 시작할지 | 실행 |

주의할 점이 있습니다.

- **깨우기 방식의 기본값은 실행 경로에 따라 다릅니다.** substrate 문서는 기본을 `implicit`이라고 합니다. 이 저장소처럼 Locust 웹 API로 시작하면 Locust 쪽 기본값인 `explicit`이 전달됩니다(소스, 우리 결과에 `ResumeActor` 행이 나오는 것으로 실행 확인). 옵션을 생략하고 substrate의 `runner.py`로 직접 돌리면 `implicit`이 적용됩니다(소스).
- **행 이름이 방식에 따라 바뀝니다.** `sync`면 `SuspendActor`, `async`면 `SuspendActorAsync` 행이 나옵니다. `implicit`이면 `ResumeActor` 행이 없습니다(실행). 결과를 비교할 때 행 이름이 다르다는 점에 주의합니다.
- **turnover는 부하 생성기(locust pod)를 다시 띄워야 합니다.** 한 번 정지 신호를 받은 부하 생성기는 turnover를 다시 돌리지 않습니다(소스·문서). `06_run_load.sh`가 매번 다시 띄우는 이유입니다.

### 3.3 부하의 모양을 바꾸는 방법 (이 저장소 스크립트는 미지원)

substrate 부하 도구에는 시간에 따라 부하를 바꾸는 "shape"가 세 가지 있습니다(소스). 쓰려면 Locust를 띄울 때 shape 파일을 함께 지정해야 하고, 이 저장소의 스크립트는 그 경로를 제공하지 않습니다.

| shape | 하는 일 | 쓰는 방법 |
|---|---|---|
| 사다리 (`ladder_shape.py`) | `사용자수:시간[@target_rps]`를 쉼표로 이어 단계적으로 올림. 예: `10:3m@1,10:3m@2,10:3m@4` | `--ladder` 옵션. 단계는 3분 이상 권장(문서) |
| 버스트 (`burst_shape.py`) | 30초 주기 중 처음 10초 동안 사용자 수를 1 → 2 → 3으로 올리고, 나머지 20초는 그대로 둠. 값은 코드에 고정 | 파일을 지정하면 적용 |
| 일괄 생성 (`spawn_shape.py`) | `spawn` 클래스 전용 | 파일을 지정하면 적용 |

사다리 없이도 같은 효과를 낼 수 있습니다. `target_rps`나 세션 수를 바꿔 가며 `06_run_load.sh`를 여러 번 실행하면 됩니다. 실행 사이에 상태가 초기화되므로 오히려 비교하기 쉽습니다.

## 4. 대본으로 Agent의 행동 정하기

대본은 YAML 파일입니다. 단계마다 "이 단계 전에 얼마나 자는가(`think`)"와 "깨어나서 무엇을 하는가(`ops`)"를 적습니다.

```yaml
name: my-agent
min_actor_memory: 512Mi        # 이 대본을 돌리는 데 필요한 Actor 메모리 한도
steps:
  - name: 01_load_context
    agent: loads context into RAM
    think: 1s                  # 이 단계 전에 자는 시간
    ops:
      - fill_ram: {key: ctx, size: 64Mi}
      - ping: {}
```

### 4.1 쓸 수 있는 동작 (소스)

| 동작 | 인자 | Actor 안에서 일어나는 일 |
|---|---|---|
| `fill_ram` | key, size | 메모리 배열을 만들어 **무작위 바이트**로 채움. 다음 바퀴에는 같은 자리를 다시 무작위로 덮어씀 |
| `churn_ram` | key, size | 배열의 일부를 다시 무작위로 덮어씀. 매번 다른 구간을 건드려, 재울 때마다 바뀐 메모리가 생김 |
| `walk_ram` | key | 배열 전체를 4 KiB마다 한 바이트씩 읽음. 깨운 직후 메모리를 실제로 불러오는 비용이 드러남 |
| `write_disk` | key, size | **무작위 바이트**로 파일을 씀. fsync는 하지 않음 |
| `ingest` | key, size | 부하 생성기가 보낸 데이터를 파일로 씀 (다운로드 흉내). 보내는 데이터는 무작위 바이트이고 모든 세션이 같은 내용을 받음 |
| `read_disk_digest` | key | 파일을 읽어 해시만 계산 |
| `read_disk_data` | key | 파일 내용을 읽어 응답으로 돌려보냄 (디스크 읽기 + 네트워크) |
| `burn_cpu` | millis, parallel | 정해진 시간 동안 CPU를 씀 |
| `ping` | 없음 | 왕복 한 번 |
| `dwell` | millis | 요청 없이 깨어 있는 채로 기다림 (모델 응답이나 사람 입력을 기다리는 시간) |

데이터에 관해 알아 둘 점입니다.

- 파일은 Actor의 루트 파일시스템에 쓰입니다. 따로 볼륨을 붙이지 않습니다(소스). 그래서 디스크에 쓴 내용도 snapshot에 포함됩니다.
- 메모리와 파일 모두 무작위 바이트라 압축이 거의 안 됩니다. 디렉터리 크기로 보면 Actor당 로컬 157 MiB가 객체 스토리지 150 MiB였고, 다른 실행에서는 170 MiB가 164 MiB였습니다(실행 2건). substrate 문서나 코드에 압축률에 관한 언급은 없습니다.
- `burn_cpu`는 시간을 채우는 방식이라, CPU가 모자라도 단계 시간은 그대로입니다. CPU 경합은 단계 시간이 아니라 별도의 처리율 지표에서 봐야 합니다(소스).

### 4.2 검사 규칙 (실행 / 소스)

대본은 Actor를 만들기 전에 검사됩니다. `bin/boomer-worker --check-agentsession-script <파일>`로 미리 볼 수 있고, `05_deploy_benchmark.sh`가 이 검사를 먼저 합니다.

- `min_actor_memory`는 대본이 쓰는 메모리와 디스크의 합 이상이어야 합니다.
- 배포한 Actor 메모리 한도(`ACTOR_MEMORY`)가 `min_actor_memory`보다 작으면 부하 생성기가 실행을 거부합니다.
- `churn_ram`·`walk_ram`은 앞에서 `fill_ram`한 key만, 읽기는 앞에서 쓴 파일만 가리킬 수 있습니다.
- 모든 단계에 `think`가 0보다 커야 합니다.

### 4.3 대본 다섯 가지

이 저장소의 대본 둘과 substrate에 내장된 대본 셋입니다. 단계 수, 메모리, 디스크, 필요한 Actor 메모리는 검사기 출력으로 확인했습니다(실행). 대기 시간 합계와 CPU 시간은 대본 파일에서 계산했습니다(소스). 실제 부하로 돌려 본 것은 `smoke-5step`뿐입니다.

| 대본 | 단계 | 한 바퀴의 대기 시간 | 메모리 | 디스크 | 필요한 Actor 메모리 | 무엇을 흉내 내나 | 돌려 봤나 |
|---|---|---|---|---|---|---|---|
| `workloads/smoke-5step.yaml` | 5 | 9초 | 64Mi | 약 24Mi | 512Mi | 동작 확인용 작은 Agent | 실행 |
| `workloads/agent-1g.yaml` | 5 | — | 640Mi | 약 96Mi | 1536Mi | 메모리가 큰 Agent | 검사만 |
| 내장 `coding-session` | 20 | 69초 (단계당 2~8초) | 96Mi | 약 98Mi | 1Gi | 코딩 Agent의 작업 한 건. CPU 약 40초 사용 | 검사만 |
| 내장 `personal-assistant` | 61 | 24시간 (2분~3시간) | 960Mi | 약 29Mi | 1536Mi | 항상 켜져 있는 비서형 Agent의 하루 | 검사만 |
| 내장 `personal-assistant-light` | 61 | 24시간 | 28Mi | 약 29Mi | 256Mi | 같은 하루, 메모리만 작게 | 검사만 |

내장 대본을 이 저장소 스크립트로 쓰려면 파일 경로를 주면 됩니다.

```bash
ACTOR_MEMORY=1Gi scripts/05_deploy_benchmark.sh \
  src/substrate/internal/benchmarking/boomer/agentsession/scripts/coding-session.yaml
```

- `personal-assistant` 계열은 하루를 그대로 재현하므로 `agentsession_think_scale=0.02`와 함께 쓰도록 만들어졌습니다(문서). 이 배율은 대기 시간에만 적용됩니다. 깨어서 기다리는 시간(`dwell`)과 CPU 사용 시간은 줄지 않으므로, 한 바퀴는 약 30분보다 깁니다(소스).
- substrate 문서에 따르면 `coding-session`은 Actor 메모리 512Mi에서 메모리 부족으로 죽고, 실제 최대 사용량은 약 320Mi였습니다(문서).

## 5. 패턴별 특징

### 5.1 agentsession 일반 모드

- **동작.** 세션마다 Actor 1개를 만들고 대본을 끝없이 반복합니다. 단계마다 "대기 → 깨우기 → 동작 → 재우기" 순서입니다(소스).
- **부하가 정해지는 방식.** 세션 수 ÷ (대기 + 깨우기 + 동작 + 재우기 시간)입니다. 재우기가 느려지면 그 세션의 다음 요청도 늦어져서 부하가 저절로 줄어듭니다.
- **볼 행.** `SuspendActor`(또는 `SuspendActorAsync`), `TimeToWake`, `Step_<단계 이름>`.
- **맞는 질문.** Agent N개가 각자 일할 때 재우기·깨우기가 얼마나 걸리는가. 대본을 바꿨을 때 snapshot 크기와 쓰기량이 어떻게 변하는가.
- **주의.** 세션들이 같은 박자로 움직여 요청이 한꺼번에 몰릴 수 있습니다. 세션 수가 많으면 `agentsession_phase_in`으로 시작을 흩어야 합니다(문서). 처음 Actor를 만들자마자 한 번 재우는데, 이 "빈 Actor 재우기"가 일반 재우기 행에 섞여 들어갑니다(소스).

### 5.2 agentsession turnover 모드

- **동작** (소스, 주요 흐름은 실행으로 확인).
  1. 등록: 세션마다 Actor를 만들고 대본의 1단계만 실행한 뒤 재웁니다. 이때의 재우기는 `SuspendActor_Register` 행에 따로 기록됩니다.
  2. 대기: 마지막 등록 뒤 60초를 기다립니다. 이 값은 코드에 고정돼 있습니다.
  3. 채우기: 자는 세션 중 `agentsession_awake`개를 깨웁니다.
  4. 교체: 1초마다 `target_rps`만큼, 쉬고 있는 깨어 있는 세션 하나를 재우고 자는 세션 하나를 깨웁니다. 깨어난 세션은 대본의 다음 단계 하나를 실행합니다. 대본의 대기 시간은 무시됩니다.
- **부하가 정해지는 방식.** 목표 속도는 `target_rps`지만, 교체는 "쉬고 있는 깨어 있는 세션"과 "자는 세션"이 둘 다 있을 때만 일어납니다. 못 채운 몫은 한 번 분량까지만 다음으로 넘기고 나머지는 버립니다(소스). 그래서 시스템이 느리면 실제 속도가 목표보다 낮아집니다. 우리 실행에서 목표 초당 1회에 실제 0.72회였습니다(실행).
- **볼 행.** `SuspendActor`, `TimeToWake`, 그리고 `summary.txt`의 `load window only` 블록(교체 구간만 잘라 계산).
- **맞는 질문.** 전체 N개 중 K개만 활성인 상태에서 계속 바뀔 때 재우기 지연, 디스크 쓰기량, 점유량이 어떻게 되는가. 이 문서의 원래 질문에 가장 가까운 패턴입니다.
- **주의.**
  - `SuspendActor_Register`는 1단계만 돈 작은 snapshot의 재우기입니다. 교체 중 재우기의 기준값으로 쓰면 안 됩니다(실행: 등록 0.36~0.47초 대 세션 1개 실행 0.83초). 기준값은 같은 대본을 세션 1개로 돌려 얻습니다.
  - 전체 실행의 평균에는 등록과 1분 대기가 섞입니다. 교체 구간만 따로 봐야 합니다.
  - 깨어 있을 수 있는 수의 상한은 worker 수가 아니라 worker 용량입니다. Actor 8개를 worker 4개에 올리자 worker마다 2개씩 깨어 있었습니다(실행). 용량이 모자라면 깨우기가 용량 오류로 재시도됩니다(소스).
  - 세션 수는 `agentsession_awake`보다 커야 합니다. 같으면 교체할 대상이 없습니다(소스).

### 5.3 glutton

- **동작.** 깨우기 → (한 번만 메모리 채우기) → ping → 재우기 → 0~0.5초 대기를 반복합니다(소스).
- **특징.** 대본이 없고 옵션으로만 조절합니다(`--mem-target`, `--mem-churn`, `--max-pings-per-wake`, 대기 시간). 동작 한 번이 밀리초 단위라, 워크로드가 아닌 플랫폼 자체의 재우기/깨우기 비용이 드러납니다.
- **맞는 질문.** 워크로드 영향을 뺀 재우기/깨우기의 최소 비용. 메모리 크기만 바꿔 가며 snapshot 비용이 어떻게 느는지.

### 5.4 sweperf

- **동작.** 녹화해 둔 실제 코딩 작업(SWE-Perf)을 Actor 안에서 다시 실행합니다. 작업을 4번에 나눠 실행하고 사이마다 재웠다 깨웁니다(문서).
- **특징.** 가짜 메모리 채우기가 아니라 실제 프로세스가 돕니다. 이 클래스만 서버가 잰 시간을 기록합니다. 다른 클래스는 요청한 쪽에서 잰 시간이라, 같은 이름의 행이라도 클래스 사이에 직접 비교할 수 없습니다(소스).
- **맞는 질문.** 실제 작업에 가까운 메모리·파일 구성에서 snapshot이 얼마나 크고 얼마나 압축되는가. 무작위 데이터의 한계를 보완할 수 있는 후보입니다.

### 5.5 resumepaused

- **동작.** Actor에 요청을 보내지 않고 깨우기와 재우기 API만 정해진 속도로 호출합니다(소스).
- **특징.** 가짜 데이터 플레인과 함께 쓰도록 만들어졌습니다. 실제 snapshot이 만들어지지 않으므로 스토리지 질문에는 맞지 않습니다.
- **맞는 질문.** 제어부(API 서버, DB)가 초당 몇 번의 깨우기를 감당하는가.

## 6. 범용성: 무엇을 대표하고 무엇을 못 하는가

| 실제 상황 | 가장 가까운 패턴 | 대표하는 정도 | 빠지는 것 |
|---|---|---|---|
| 코딩 Agent 여러 개가 작업 | 일반 모드 + `coding-session` | 깨어남과 잠듦의 리듬, CPU·디스크·메모리 사용 순서는 흉내 냄 | 실제 프로세스 구조, 압축되는 데이터, 모델 응답 지연의 분포 |
| 많은 Agent 중 일부만 활성 | turnover 모드 | 활성 비율과 교체 속도를 직접 정할 수 있음 | 실제 요청 도착의 불규칙함(몰림, 시간대별 변화) |
| 항상 켜진 비서형 Agent | 일반 모드 + `personal-assistant(-light)` | 하루의 깨어남 61번과 간격을 흉내 냄 | 시간을 줄여 돌리므로 재우기 사이의 실제 간격에서 생기는 효과(로컬 사본 삭제 30분 등) |
| 스토리지에 걸리는 쓰기 | 위 패턴 + 큰 대본 | 쓰기 경로(로컬 디스크 → 압축 → 객체 스토리지)는 실제 그대로 | 압축률, 중복 제거 효과, 실제 snapshot 크기 |
| 제어부 한계 | `resumepaused` | 제어부 비용만 분리 | 스토리지와 복원 |

공통 한계는 세 가지입니다.

- **데이터가 무작위입니다.** 압축과 중복 제거가 듣지 않아, 객체 스토리지 쓰기량과 업로드 시간이 실제보다 불리하게 나옵니다. 반대로 실제 Agent는 메모리가 훨씬 클 수 있어, 어느 쪽으로 치우치는지는 실제 Agent를 재 봐야 압니다.
- **LLM이 없습니다.** 모델 응답을 기다리는 시간은 `think`(자는 시간)와 `dwell`(깨어서 기다리는 시간)로만 표현합니다. 어느 쪽으로 볼지에 따라 재우기 빈도가 크게 달라집니다.
- **요청이 규칙적입니다.** 한꺼번에 몰리는 상황은 `spawn` 클래스(일괄 생성)나 세션을 한꺼번에 시작하는 방식으로 따로 만들어야 합니다. 내장 버스트 shape는 최대 3명으로 고정돼 있어 그대로는 쓰기 어렵습니다.

### GKE용 벤치마크 저장소(agent-infra-benchmarking)와 비교

같은 주제의 공개 저장소에는 실제 Agent 소프트웨어를 돌리는 워크로드가 있습니다(해당 저장소 소스로 확인, 실행하지 않음).

| | substrate 부하 도구 (이 문서) | agent-infra-benchmarking의 OpenClaw 워크로드 |
|---|---|---|
| Actor 안에서 도는 것 | 메모리·디스크·CPU를 쓰는 시험용 서버 | 실제 OpenClaw 게이트웨이(Node.js). 셸 명령을 실제로 실행 |
| LLM | 없음 | 모의 LLM. 정해진 6번의 응답(도구 호출 5번)을 지연 없이 돌려줌 |
| Actor 메모리 | 배포할 때 정함(substrate 기본 256Mi, 이 저장소 512Mi). 대본은 필요한 최소값을 선언 | 기본 2Gi. gVisor에서 256Mi면 메모리 부족으로 죽음 |
| 부하 조절 | 세션 수, 교체 속도, 대본, 대기 시간 배율 | 사용자 수, 대기 시간(0~0.5초), 활성 Actor 수(density) |
| 실행 환경 | Kubernetes면 됨 | 실행기가 GKE 클러스터를 직접 만들어 씀(개발용으로 남겨 재사용하는 옵션은 있음). 다른 곳에 이미 있는 클러스터를 지정하는 옵션은 없음 |
| 사내 서버에서 | 이 저장소 스크립트로 실행 가능 | 지원되는 경로 없음. 이미지 4개를 직접 빌드하고 매니페스트를 손으로 적용해야 함 |

OpenClaw 워크로드는 "실제 Agent 프로세스의 메모리"를 볼 수 있다는 점에서 더 현실적입니다. 다만 매번 같은 궤적을 돌고 모델 지연이 0이라, 그것도 실제 사용과는 다릅니다. 사내 서버에서 쓰려면 실행기를 우회하는 작업이 필요하고, 그 작업량은 직접 해 보지 않아 가늠하지 못했습니다.

## 7. 신뢰도: 결과를 어디까지 믿을 수 있는가

### 7.1 측정 방식에서 오는 한계

- **요청이 시스템 속도에 맞춰 줄어듭니다.** 모든 패턴에서 가상 사용자는 앞 요청이 끝나야 다음 요청을 보냅니다(소스). 실제 서비스처럼 요청이 계속 들어오는 상황보다 지연이 작게 나올 수 있습니다. turnover도 교체할 대상이 없으면 밀린 몫을 대부분 버립니다. **목표 속도와 실제 속도를 같이 보고, 실제 속도가 목표에 못 미치면 "한계에 닿았다"고 읽어야 합니다.**
- **"실패 0건"은 부하 생성기 기준입니다.** 깨우기는 자리가 없으면 최대 60초까지 다시 시도합니다. 시도마다 실패가 `ResumeActor`(implicit이면 `WakeFirstTouch`) 행에 하나씩 기록되고, 기다린 시간의 합은 `TimeToWake`에만 들어갑니다(소스). 우리 실행은 실패가 0건이었으므로, `TimeToWake`가 길어진 것은 재시도 때문이 아니라 깨우기 자체가 느려진 것입니다.
- **시간은 요청한 쪽에서 잽니다.** `agentsession`의 재우기·깨우기 행은 요청 쪽 시간입니다(소스). 노드 안의 구간별 시간(`phases.txt`)보다 세션 1개에서 약 0.1초, 교체 부하에서 약 1초 깁니다(실행). Locust의 백분위는 값이 클수록 거칠게 묶입니다. 10초 이상은 1초 단위라서, 11초나 p95 15~16초 같은 값은 ±0.5초 해상도로 읽어야 합니다.
- **통계는 정지 전에 끊깁니다.** 종료할 때의 재우기는 기록되지 않습니다(소스). 삭제는 이 저장소 스크립트가 정지 전에 통계를 저장하기 때문에 빠집니다.
- **sync와 async는 재는 범위가 다릅니다.** async의 재우기 시간에는 업로드가 빠져 있습니다. 업로드 부담은 5분 뒤 백그라운드에서 생기므로, 실행 시간이 그보다 짧으면 측정 창 밖으로 빠집니다(소스). 짧게 돌려 본 결과도 그렇습니다. async 90초 실행에서 재우기 중앙값은 0.18초, 재우기 1회당 디스크 쓰기는 약 190 MiB였습니다. sync(세션 1개 실행)는 각각 0.83초, 약 336 MiB였습니다(실행. 세션 수와 대기 시간이 달라 참고용).

### 7.2 반복했을 때의 흔들림 (실행)

같은 조건(turnover, 12개 중 3개 활성, 목표 초당 1회, sync)을 다시 돌린 결과입니다.

| 설정 | 재우기 중앙값 | 재우기 p95 |
|---|---|---|
| 업로드 한도 기본(512Mi), 3회 | 9.8초 / 8.9초 / 11초 | 16초 / 16초 / 15초 |
| 업로드 한도 2Gi, 2회 | 2.3초 / 3.8초 | 7.1초 / 18초 |

- 기본 설정은 중앙값이 ±10% 안팎으로 움직였고 p95는 안정적이었습니다.
- 한도를 올린 설정은 두 번의 p95가 2.5배 차이 났습니다. 시스템이 한계 근처에서 움직일 때는 실행마다 결과가 크게 달라집니다.
- 실행 안에서도 값이 변합니다. 한도 2Gi의 두 번째 실행에서 업로드 구간은 첫 1분 0.4~0.6초였다가 2분 30초 뒤 10초대가 됐습니다. **5분짜리 실행 하나의 중앙값은 그 5분의 평균일 뿐입니다.** 30초 단위로 잘라 추세를 같이 봐야 합니다(`scripts/analyze_uploads.py`의 입력 기록으로 가능).

### 7.3 실행 길이와 반복에 관한 권고

두 저장소의 문서가 밝힌 기준입니다(문서).

- substrate: 사다리의 한 단계는 3분 이상. Prometheus 지표의 수집 주기가 60초라 그보다 짧으면 잡음이라는 이유입니다. Locust 통계와 이 저장소의 1초 수집에는 그대로 적용되지 않습니다.
- GKE 저장소: "실행 한 번은 표본 하나"입니다. 비교는 반복 실행끼리 하고, p50을 대표값으로 쓰되 p99는 반복 사이의 범위와 함께 적으라고 권합니다.
- GKE 저장소: 같은 클러스터에서 반복할 때는 측정 실행 전에 준비 실행을 한 번 돌려 요약에서 빼고, 모든 사용자가 시작한 뒤 일정 시간이 지난 구간만 집계합니다.

substrate 문서에는 몇 번 반복하라는 기준이나 편차에 관한 언급이 없습니다.

### 7.4 근거 수준 정리

| 내용 | 근거 |
|---|---|
| 일반 모드 세션 4, turnover(12/3/1), sync | 실행 (2~3회) |
| 일반 모드 세션 1, sync | 실행 (1회) |
| async, implicit, 대기 시간 배율 | 실행 (1회, 90초) |
| worker 하나에 Actor 여러 개 | 실행 (1회) + 소스 |

| 내장 대본 셋의 구성 | 검사기 출력으로 확인. 부하 실행은 안 함 |

| Linux 서버, microVM, 12개 초과 규모 | 미확인 |

## 8. 서버 검증에서 권하는 순서

1. **기준값.** 쓸 대본을 세션 1개로 2~3분 돌려 겹침 없는 재우기·깨우기 시간과 snapshot 크기를 잡습니다. 같은 조건을 3회 이상 반복해 흔들림의 폭을 먼저 봅니다.
2. **일반 모드로 겹침 늘리기.** 세션 수를 4, 8, 16…으로 올립니다. worker 하나에 몰리는 영향을 보려면 worker 수도 바꿔 봅니다.
3. **turnover로 교체 속도 올리기.** 전체 수와 깨어 있는 수를 정하고 `target_rps`를 단계적으로 올립니다. 실제 속도가 목표를 못 따라가기 시작하는 지점이 그 구성의 한계입니다.
4. **대본 키우기.** `agent-1g.yaml`이나 `coding-session`으로 바꿔 snapshot 크기에 따른 변화를 봅니다. 필요한 쓰기 속도는 초당 재우기 횟수 × snapshot 크기로 어림합니다. sync이고 로컬 snapshot과 객체 스토리지가 같은 디스크에 있으면(이 저장소의 kind 구성) 그 2배, 둘이 분리돼 있거나 async면 약 1배입니다.
5. **async로 다시.** 기본값인 async에서 재우기 시간과 업로드 적체를 따로 봅니다. 실행 시간은 업로드 지연(5분)보다 충분히 길게 잡습니다.
6. **업로드 한도.** sync에서 재우기가 길면 디스크보다 먼저 `--upload-memory-budget`을 의심합니다. 올릴 때는 노드의 CPU와 메모리 여유를 함께 봅니다.

실제 Agent의 메모리 구성과 압축률은 이 도구로 알 수 없습니다. 실제 Agent 하나의 snapshot 크기와 압축률을 따로 재서, 대본의 크기를 그 값에 맞추는 것이 가장 큰 보정입니다.
